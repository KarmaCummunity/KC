# 14 — Responsive Desktop (FR-RESP-*)

**Status (source checkpoint 2026-11-24, #1862):** Shell primitives and responsive wiring exist. Side-by-side chat and split-auth wiring remain planned. Mobile polish is partial; unit/snapshot coverage is not proof that the full manual device matrix ran.
**Owner:** Current issue/PR ownership is tracked in GitHub, not by an autonomous-loop label in this document.
**Design doc:** `docs/SSOT/archive/superpowers/specs/2026-05-22-responsive-desktop-design.md`

This domain covers adapting the mobile app to desktop browsers (≥ 768px viewport) without regressing mobile (< 768px). Strategy and decisions captured in `D-RESP-001`.

## FR-RESP-001 — Shell primitives (foundation)

**Status:** Implemented primitives; historical staging-only restrictions below are superseded by FR-RESP-002's root wiring.

**ACs:**
- AC1. `@kc/ui` exports a `BREAKPOINTS` constant with four named widths (`mobile`, `tablet`, `desktop`, `wide`) and a `useBreakpoint()` hook returning the current token.
- AC2. `@kc/ui` exports `AsideProvider`, `useAside` and `useAsideContent`; the context itself is private. The hook can publish safely at every breakpoint, while mobile chrome does not display the desktop panel. The earlier public-context/no-op wording is historical.
- AC3. `@kc/ui` exports an `AsidePanel` display component.
- AC4. `apps/mobile/src/components/shell/` contains `NavigationRail`, `SplitAuthLayout`, `AppShell`, and a shared `tabs.config.ts` consumed by both `TabBar` (existing) and `NavigationRail` (new).
- AC5. Historical foundation staging required a default-off `SHELL_V2_ENABLED` flag. Current source uses it only for the developer preview: on in `__DEV__` unless `EXPO_PUBLIC_SHELL_V2=0`, always off outside development. It does not gate the responsive production shell.
- AC6. A dev-only route at `/dev/shell-preview` mounts when `SHELL_V2_ENABLED` and showcases all four breakpoints.
- AC7. A baseline snapshot test at 375px viewport guards the mobile invariant.
- AC8. Historical foundation-only scope prohibited changing existing layouts except the tabs-config refactor. Superseded for subsequent delivery by FR-RESP-002's explicit root-layout wiring; retained here as phase history, not a current ban on that implementation.

## FR-RESP-002 — Wire shell to (tabs)

**Status:** ✅ Done

`ShellWithResponsiveChrome` is wired at the root. Web at >=768 uses `AppShell`; native and narrower web use floating mobile chrome. The old instruction to flip `SHELL_V2_ENABLED` no longer describes the runtime gate: that flag controls the dev preview only.

- *(KC#2381, 2026-11-16)* The navigation rail and the aside panel are shown to signed-in members only. A signed-out visitor (welcome, About, legal pages, the public research form) and everyone on the sign-in, onboarding, `auth/callback`, `auth/verify` and public research surfaces (`FR-RESEARCH-001` AC2) get the page alone: every rail item leads to a member route. The rule is `shellNavigationRailVisible` (`navigation/shellChromePolicy.ts`). The rail stays on a chat thread, where only the floating tab bar of the phone layout is hidden.

## FR-RESP-003 — Aside panels for feed, donations, profile, search

**Status:** ✅ Done

Each screen publishes contextual aside content via the focus-aware `useScreenAside(...)` wrapper (`useAside` gained an `enabled` arg so unfocused-but-mounted tab scenes withdraw their content):
- Feed → `GivingWorldsAside` (curated giving-world shortcuts; no trending/suggested-follows backend exists at MVP, so the curated list stands in).
- Search → `RecentSearchesAside` (store-backed; a tap runs the query in the screen via the `requestedQuery` handshake on `searchStore`).
- Donations hub → `CommunityStatsAside` (live `community_stats` snapshot, shared query key with the stats screen).
- Profile (own, open + closed tabs) → `ProfileStatsAside` (karma, given/received, open/closed counts, link to `/stats`).

## FR-RESP-006 — Mobile platform polish & bottom-bar safety

**Status:** 🟡 In progress

Cross-cutting fix for content cropping behind the floating tab bar on mobile + platform-aware paper cuts. Audit-driven, mapped 1:1 to plan `docs/SSOT/archive/superpowers/plans/2026-05-25-mobile-platform-polish-audit.md`.

**ACs:**
- AC1. Every screen where `useShellTabBarVisibility()` returns `true` reserves enough bottom inset on its scrollable content (or on its floating footer) that the last row is fully visible above the floating-pill TabBar across the **full supported-device matrix**: iPhone SE 2nd/3rd gen (375×667, 20pt top inset, 0pt bottom), iPhone 8 (375×667, 20pt/0pt), iPhone 12/13 mini (375×812, 50pt notch, 34pt home-indicator), iPhone X / XR / 11 / 11 Pro / 11 Pro Max (375–414×812–896, 44pt notch), iPhone 12–13 (390×844, 47pt notch), iPhone 14 Pro through 16 Pro / 16 Pro Max (393–430×852–932, 59pt Dynamic Island); small Android (360×640, gesture-nav or 3-button-nav), standard Android (393×873, Pixel 6/7/8), large Android (412×915, Pixel Pro), Android foldable closed (≈360×780, Z Fold outer); mobile web at 320 / 360 / 375 / 414 / 430 viewport widths (Mobile Safari + Chrome). Holds at default Dynamic Type **and** at the OS-level "Larger Text" / "Largest" setting (Android font scale 1.0 → 1.3).
- AC2. The `Screen` primitive (`apps/mobile/src/components/ui/Screen.tsx`) accepts a `tabBarInset?: boolean` prop (default `true`) and adds `useShellTabBarScrollInset()` to its scroll content's `paddingBottom` automatically when on and the tab bar is visible.
- AC3. No screen carries `edges={['bottom']}` on its root SafeAreaView while `useShellTabBarVisibility()` is `true` for that screen.
- AC4. `useDirectionalBackIcon()` (`apps/mobile/src/components/ui/MirroredIcon.tsx`) returns the back glyph named for LTR — `chevron-back` on iOS (Apple HIG), `arrow-back` on Android (Material 3) and on web — and the back affordances (`BackButton`, chat, onboarding and auth headers, the map) render it through `<MirroredIcon>`, which turns it around in RTL; no call site hard-wires a Hebrew-only `arrow-forward`.
- AC5. `useKeyboardVerticalOffset()` returns a sensible value per platform (iOS: real header height from `useHeaderHeight()` + top inset, with explicit override for custom-header screens; Android / web: 0) and replaces every hardcoded `keyboardVerticalOffset={88}`.
- AC6. `Text` elements in tight rows (`PostCard`, `InboxChatRow`, `MessageBubble`) cap dynamic-type at `MAX_FONT_SCALE_TIGHT = 1.35` via `maxFontSizeMultiplier`; long-form copy uses `MAX_FONT_SCALE_FLEX` (2.0 native / 1.5 web).
- AC7. Snapshot tests at `apps/mobile/src/components/ui/__tests__/Screen.tabBarInset.test.tsx`, `Screen.nativeHeader.test.tsx`, and `Screen.deviceMatrix.test.tsx` prove that the `Screen` primitive's `contentContainerStyle.paddingBottom` includes the tab-bar height when visible and excludes it when suppressed, across six representative device profiles.
- AC8. Mobile invariants from FR-RESP-001 (375px snapshot) and FR-RESP-002 (no shell regression) still pass.
- AC9. Screens registered with `headerShown: true` (native Expo Router header) do **not** double-pad: the `Screen` primitive's effective edges drop `'top'` when its new `hasNativeHeader` prop is set.
- AC10. `useKeyboardVerticalOffset()` reads the actual rendered header height when available (`useHeaderHeight()` from `@react-navigation/elements`); explicit numeric override for custom-header screens (e.g. `chat/[id]`).
- AC11. Dynamic Type policy split: `MAX_FONT_SCALE_TIGHT = 1.35` on fixed-height grid cells / one-line rows; `MAX_FONT_SCALE_FLEX = Platform.select({ ios: 2.0, android: 2.0, web: 1.5 })` on long-form body. Recorded as `D-RESP-006` in `docs/SSOT/DECISIONS.md` (in PR D, not this PR).
- AC12. App-level platform preconditions encoded in `app.json`: `expo.android.softwareKeyboardLayoutMode = "resize"` and `expo.androidStatusBar.translucent = true`.
- AC13. Left/right safe-area insets honored on the floating TabBar wrapper and on every scrollable's `contentContainerStyle` that previously used only horizontal `spacing.base`. Verified on iPhone 16 Pro Max landscape (`insets.left = 59`) and Galaxy Z Fold landscape sanity check.
- AC14. Mobile Safari visible-viewport fix: root `_layout.tsx` injects `html, body, #root { min-height: 100dvh; height: 100dvh; }` (with `100%` declared first as fallback). Verified by integration check.
- AC15. `FlatList` / `ScrollView` `contentContainerStyle` arrays that include the dynamic `tabBarPad` are memoized with `useMemo` — prevents inner ScrollView content-size cache invalidation on iOS when route changes trigger re-renders.
- AC16. Manual matrix executed across all four tiers (iOS phones from SE through 16 Pro Max; Android compact + standard + large + foldable closed; iPad mini portrait + iPad 10th gen + iPad Pro 13" landscape; Mobile Safari + Chrome at 320/360/375/414/430/768/1024/1440), with OS-Largest-Text setting on. Failed cells filed as `TD-1xx` entries.
- AC17. Hebrew typography minimums (from `skills-il/localization@israeli-ui-design-system`): `typography.body.lineHeight / typography.body.fontSize ≥ 1.7`; `typography.bodyLarge.lineHeight / typography.bodyLarge.fontSize ≥ 1.7`; minimum `fontSize ≥ 13` on every body-or-larger token. Tested via `typography.hebrewMinimums.test.ts`.
- AC18. Directional-icon mirroring policy: every directional icon (chevron, arrow, caret, play/forward/backward) renders through the `<MirroredIcon>` primitive (`apps/mobile/src/components/ui/MirroredIcon.tsx`), which applies `transform: scaleX(-1)` only when the layout runs RTL (`isLayoutRtl()`: `document.dir` on web, `I18nManager.isRTL` on native). Non-directional icons (search, home, settings, bell, gear) MUST NOT mirror. The brand guard's `unmirroredDirectionalIcon` rule freezes the remaining raw directional glyphs per file (spec 17 §4.2) and ratchets them down.
- AC19. Hebrew UX copy register: locale strings for buttons, errors, toasts, and form labels are UX-direct — short and direct, calls-to-action ≤4 words, no padded softeners (`נשמח אם`, `אנא`, `ייתכן שכדאי`). Rules in `docs/spec/17_brand_and_design_system.md` §7 (D93). Audited by the copy-voice guard (`apps/mobile/src/__tests__/copyVoiceGuard.test.ts`, inside `pnpm test`; shortcut `pnpm lint:hebrew-register` from `app/`) as a ratchet: existing findings are frozen in `apps/mobile/copy-voice.baseline.json` and every locale file a PR changes must be clean.
- AC20. Gender-neutral UX strings (Option C): every UX locale string for the current user uses neutral phrasing — the infinitive (`ללחוץ`, `יש להזין`, `ניתן לבחור`) — instead of masculine or feminine singular forms (spec 17 §7.2). Sentence-initial singular imperatives and singular address (`אתה`, `הנך`, `תוכלי`) are audited by the same guard; strings about *another* user are out of scope.
- AC21. Free-text inputs use auto direction: every `<TextInput>` whose content can be either Hebrew or English sets `textAlign="auto"` and `writingDirection: 'auto'`. Numeric / single-direction fields keep fixed direction.
- AC22. Shadows + gradients have no horizontal physical offsets: audited by `app/apps/mobile/scripts/lintRtlShadows.mjs`; fails CI if a future PR introduces a `shadowOffset.width !== 0` without an `I18nManager.isRTL` guard.
- AC23. Re-tapping the active tab never re-mounts its screen (#1633). On the tab's root screen the press does nothing (no push, no replayed entry animation); on a nested screen of that tab it unwinds to the tab root (`router.dismissTo`), whose screen stays mounted underneath. The composer "+" is the exception: re-tapping it while the create form is open closes the form (`router.back()`, or `dismissTo('/(tabs)')` when there is nothing to go back to). Other tabs open as before. One rule for the bottom `TabBar` and the desktop `NavigationRail`: `resolveTabPressAction` / `handleActiveTabRepress` in `apps/mobile/src/components/shell/tabPress.ts`. Tests: `shell/__tests__/tabPress.test.ts`, `components/__tests__/TabBar.repress.test.tsx`, Maestro `15-tab-retap-and-profile-tabs.yaml`.
- AC24. A form's sticky footer stays on screen above the software keyboard on iOS **and** Android. The app is edge-to-edge on Android (`enableEdgeToEdge`), so AC12's `softwareKeyboardLayoutMode = "resize"` does not resize the window and the form must shrink itself: `FormScreen` takes its `KeyboardAvoidingView` behavior from `resolveKeyboardAvoidingBehavior()` (`apps/mobile/src/lib/platform/keyboardVerticalOffset.ts`): `padding` on iOS, `height` on Android, none on web. Every `KeyboardAvoidingView` in the app — including the kit `BottomSheet` Modal (#2139) — takes its behavior from that resolver; the bottom sheet's Android Modal window has not been checked on a device yet (#2758) (`keyboardAvoidingBehaviorUsage.test.ts` scans the source and fails when a view omits `behavior` or sets it by hand). The source scan proves the resolver is used, not the on-screen result. Covered by `FormScreen.test.tsx` and Maestro flow `19-edit-profile-keyboard-toolbar` (save button visible with the keyboard open and after it closes).
- AC25. One form behavior everywhere. Every text input inside a `Screen`, `FormScreen`, `FormScrollView`, `BottomSheet` or `Modal` joins a form scope automatically, with no per-field wiring (a nested scope joins the enclosing one, so there is never a second toolbar; modal and sheet windows always own theirs): (a) in a form of two or more fields the keyboard toolbar (Previous / Next / Done) and the return key (Next, then Done on the last field) follow the **on-screen reading order** — top to bottom, and within one row from the reading-start edge (right in Hebrew; the layout direction is read the same way on web, from the document); fields are grouped into rows before they are ordered, so the order is well defined; each scope has its own iOS toolbar, so a sheet or modal over a form never drives the form behind it; Next from a field that just became disabled does nothing (it never jumps back to the top); disabled fields are skipped; on a phone, the field Next / Previous (or the return key) lands on is scrolled fully into view above the keyboard, and the screen stays put when it is already visible (`revealFieldAboveKeyboard`, `useKeyboardTop`); multiline fields keep their newline key; a lone field (search box, note) gets no toolbar; an explicit `returnKeyType` wins. (b) A field that **newly** shows an error scrolls into view (top-most first when several appear together); an error present on first render, an error on the field being typed in, and an error a field shows on blur while the member has moved on to type in another field never move the screen; a rejected submit with new errors and a bumped submit signal scroll once. After the jump the screen reader moves to the field (native). A form can re-trigger the jump after a rejected submit with unchanged errors (`FormScrollView` and `FormScreen` take `jumpToProblemSignal`; also `useScrollToFirstInvalid`). Non-text sections (photo picker, pickers) take part via `useFormScopeAnchor`; a bare input component joins via `useFormScopeField`. A screen with text fields must not scroll through a bare `ScrollView` (guard: `__tests__/formScopeGuard.test.ts`). Code: `components/ui/formScope.ts`, `FormScope.tsx`, `useFormScopeField.ts`, `FormScrollView.tsx`, `lib/platform/formFieldOrder.ts`. Tests: `components/ui/__tests__/formScope.test.tsx`, `formScope.regressions.test.tsx`, `formScope.primitives.test.tsx`, `JumpOnSignal.test.tsx`, `lib/platform/__tests__/formFieldOrder.test.ts`.
- AC26. The keyboard matches the content. `TextField` takes `inputKind` (`text | name | email | phone | integer | decimal | url | date | time | streetNumber | password`), mapped in `lib/platform/formTextInputHints.ts` to the keyboard type, `inputMode`, capitalisation, autocorrect and autofill hints; explicit props still win. Tests: `lib/platform/__tests__/formTextInputHints.test.ts`, `TextField.test.tsx`.
- AC27. Rejected Publish on the give / request form (`app/create.tsx`) marks the missing title / photo / address inline and scrolls to the first one on every attempt, in addition to the toast (`useCreatePostPublish`: `titleInlineMessage`, `photoInlineMessage`, `failedSubmitCount`).
- AC28. One layout for every multi-option section. Each choice among several options (category, condition, listing kind, sub-category, extra worlds, weekdays, challenge options, report category, filters) is one `ChipSelectRow` line of `Chip`s that **scrolls sideways**: no wrapping, no expand / collapse control, the same height whatever the number of options. `FilterChipRow` is the single / multi-select wrapper; hand-drawn chips and raw horizontal `ScrollView`s are not used. Tests: `filterKit/__tests__/filterKit.test.tsx`.
- AC29. One section anatomy for every form. A form is built from `FormSection`s (`components/ui/FormSection.tsx`): label with the red required star, optional hint, the control, and the message right under it when something is wrong; the section's control is outlined in red unless it draws its own error (the kit `TextField`). A section showing an error is a target of the form scope's "jump to the first problem" (AC25), so no form owns a scroll hook: the listing form, the items create / edit forms, the challenge and link forms all rely on it. The create and edit forms of an item follow the same section order (photos, title, address, category, condition, description, urgency, exposure). A rejected submit explains itself next to the fields (the link form no longer greys out its button). Tests: `ui/__tests__/FormSection.test.tsx`, `__tests__/formScopeGuard.test.ts`. Field problems are never only a dialog or a toast: the auth forms (sign-in, sign-up, forgot and reset password; `AnimatedAuthInput` takes `errorText`) and the profile forms (edit profile, onboarding basic info, the basic-info soft gate) show each one under its field and keep their submit enabled, so pressing it explains what is missing and jumps to the first problem (`FormScreen` / `FormScrollView` `jumpToProblemSignal`); the profile forms share one validator (`lib/profileFieldErrors.ts`, `useProfileFieldErrors`). The items edit form marks the title, photo and address with the create form's rules (`postFieldErrors`) and its Save stays enabled; the challenge form runs the domain rules before sending and marks the field a refusal is about (`challengeFormProblem`). Every listing edit — from the post screen or from "my listings" — opens the same full editor (`hrefForPostEdit`); the title-and-summary-only screen is gone. A failure that belongs to no field (a refused sign-in, a network error) stays a dialog.
- AC30. Exposure settings in every post form. Every form that publishes a post ends with the same closed "exposure settings" block (`post/ExposureSettingsSection.tsx`): the audience (public / followers / only me; followers is offered only to a private profile), the address level (not offered to a ride, which has no address of its own) and the identity mask. It is on the items create and edit forms and on every marketplace listing form, create, edit and republish (`useListingExposure`; `createListing` / `updateMyListing` write `visibility` and `location_display_level`; the owner's mask is saved like the items form's: a new listing writes an identity row only when masked — "only me" always masks — and an edit rewrites an existing row (`syncOwnerPostActorIdentity`). An edit waits for the stored mask before it can be saved and keeps a stored followers-only audience after the profile turned public (`FR-POST-009` AC4). If a new listing's mask cannot be saved, the listing is withdrawn and the error shown, so it never stays live unmasked.) A recurring ride or event is published date by date with the usual defaults, so the block is not shown while a recurrence is set. Link forms (not posts) and challenges (own RPC) do not have it. Tests: `hooks/__tests__/useListingExposure.test.tsx`, `ListingCreateForm.exposure.test.tsx`, `useListingCreateForm.test.tsx`, `saveMaskOrWithdraw.test.ts`, `listingWrites.test.ts`, `listingDetailReads.test.ts`, `supabase/tests/036_post_actor_identity.sql`.
- AC31. The keyboard of a field is set by its kind (AC26 of this file, `inputKind`) in every form, for the kit `TextField` and the auth input alike; date and time values are picked, not typed. Every keyboard is set this way: no form spreads `keyboardType` / `autoComplete` by hand (organization registration, quiet hours, the demo-data password, admin contact names, a knowledge question's link through the field spec's `inputKind`), and the items form's house number is the shared `StreetAddressRow` like every other address. A required field shows the red star from the `required` prop of `TextField` / `FormSection`, never typed into its label. Admin forms follow the same kit: the ledger, account, CRM-contact and timesheet forms are kit `BottomSheet`s (their own form scope), their option rows are `FilterChipRow`s, `AdminFormField` takes `inputKind` / `errorText` / `required`, and admin days (ledger, account opening, timesheet, audit and task due-date filters) are picked with `AdminDateField`, kept as the local `YYYY-MM-DD` (`lib/localDay`) so a day never moves by the UTC offset. The form-scope guard also covers `AdminFormField` screens.
