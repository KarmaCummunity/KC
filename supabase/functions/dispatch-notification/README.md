# dispatch-notification

Push worker of the notification queue. The database decides who is notified and writes the
notification centre; this function only renders text and talks to the push provider.

## One run

1. Asks the provider for the receipts that are due and forgets devices it reports as gone.
2. `kc_private.notifications_deliver_batch` — delivers a batch of `notification` outbox
   events and returns the pushes to send; `kc_private.notification_push_retry_batch` —
   claims pushes waiting for a retry.
3. `kc_private.notification_message_previews` — chat previews of the whole run, by message id.
4. Sends one message per device, at most 100 per request, 4 requests at a time.
5. `kc_private.notification_push_settle` — dead devices, retries with back-off (30 s
   doubling, capped at an hour, 5 attempts), finished events, receipt checks 15 minutes later.

The handler repeats runs until the queues are empty or 20 seconds have passed.
Concurrent invocations are safe: an event is handed to one worker only.

## Files

| File | Role |
|---|---|
| `kinds.generated.ts`, `strings.he.generated.json` | generated by `scripts/generate-notification-kinds.mjs` — never edit |
| `messages.ts` | text and per-platform message of a push (pure) |
| `dispatch.ts` | one run against the two ports |
| `types.ts` | payload contracts and the ports (`PushDatabase`, `PushTransport`) |
| `expoTransport.ts` | Expo push service |
| `postgresDatabase.ts` | the database functions over a Postgres connection |
| `handler.ts`, `index.ts` | HTTP entry, wiring |

## Decisions

- **Provider: Expo push service.** The app registers Expo push tokens, and one API reaches
  APNs and FCM. It sits behind `PushTransport`, so a direct APNs / FCM transport can replace it.
- **Text: rendered here, in Hebrew**, from the app's own locale strings (generated copy).
  The Expo message format has no localisation keys, so client-side localisation is not
  available on both platforms.
- **Platform fields come from the kind's registry row**: channel and iOS category = the
  kind's category; `high` priority and iOS `time-sensitive` only for kinds that pass quiet
  hours; `collapseId` / Android `tag` from the group key so grouped events replace each
  other; iOS `threadId` = the entity; iOS `badge` = the unread count from the database.
- Nothing logs a token, a title or a body. The response is counts only.

## Secrets (names only)

`SUPABASE_DB_URL`, `SUPABASE_SERVICE_ROLE_KEY` (built in), `EXPO_ACCESS_TOKEN`.

## Invoke

Service-role bearer only; a scheduler calls it at least every minute.

```bash
curl -X POST "$SUPABASE_URL/functions/v1/dispatch-notification" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY"
```
